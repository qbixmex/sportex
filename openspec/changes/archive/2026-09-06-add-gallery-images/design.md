## Context

The `galleries` module already exists (entity `Gallery`, admin-only CRUD at `/api/v1/galleries`, `@Auth(VALID_ROLES.ADMIN)`, uuid ids, snake_case `created_at`/`updated_at`, `PaginationDto`). Images give galleries their content. The `Announcement` entity already models Cloudinary-style media as `image_url` + `image_public_id`, and relations in the codebase use `ON DELETE CASCADE` (see `field_team`). See `proposal.md` — Why for motivation; the behavior contract lives in `specs/gallery-management/spec.md`.

## Goals / Non-Goals

**Goals:**
- A `gallery_images` table and `GalleryImage` entity with the requested fields (identifier, title, image reference, public identifier, active, created/updated dates).
- One-to-many relation Gallery → GalleryImage; deleting a gallery deletes its images via the DB FK.
- Admin-only CRUD for gallery images, scoped inside a gallery (nested under a gallery id).
- Metadata-only: no file upload handling.
- Slim API responses: images never embed the parent gallery object; delete operations (images and galleries) return only a confirmation message.

**Non-Goals:**
- No file upload / storage service integration (the image URL + public id are provided directly by the admin, per product decision).
- No public endpoints, no association with other entities.

## Decisions

- **Entity `GalleryImage`** in `src/modules/gallery-images/entities/gallery-image.entity.ts`, table `gallery_images`:

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | PK, `@PrimaryGeneratedColumn('uuid')` |
| `gallery_id` | uuid | FK → `galleries.id`; `@ManyToOne(() => Gallery, (g) => g.images, { onDelete: 'CASCADE' })` + `@JoinColumn({ name: 'gallery_id' })` |
| `title` | varchar | required |
| `image_url` | varchar | **unique**, required |
| `image_public_id` | varchar | required |
| `position` | int | optional in requests; DB default `0`; used to order the listing (ascending) |
| `active` | boolean | DB default `false` |
| `created_at` | timestamptz | `@CreateDateColumn` |
| `updated_at` | timestamptz nullable | `@UpdateDateColumn` |

  Rationale: the requested "auto increment and UUID" id is resolved as a UUID primary key auto-generated by the DB — the platform-wide convention (`@PrimaryGeneratedColumn('uuid')` everywhere). The unique `image_url` enforces "the same image cannot be registered twice" at the DB level. Alternatives considered: composite PK on `(gallery_id, image_url)` — rejected; a global unique constraint already enforces platform-wide uniqueness and the existing modules use a surrogate uuid id.

- **Gallery side:** add `@OneToMany(() => GalleryImage, (gi) => gi.gallery)` `images` to `src/modules/galleries/entities/gallery.entity.ts`. No migration needed for the relation itself. Future reads of a gallery with its images can use `relations: { images: true }`.

- **Module `src/modules/gallery-images/`:** `gallery-images.module.ts`, `gallery-images.controller.ts`, `gallery-images.service.ts`, `entities/gallery-image.entity.ts`, `dto/create-gallery-image.dto.ts`, `dto/update-gallery-image.dto.ts`, `dto/index.ts`, `gallery-images.service.spec.ts`. Module imports `TypeOrmModule.forFeature([GalleryImage, Gallery])`, `AuthModule`, `CommonModule`; registered in `src/app.module.ts`. It mirrors the `galleries`/`videos` module shape; snippets/docs of the factory blueprint are at `src/modules/galleries/`.

- **Router:** `GalleryImagesController` at `@Controller('galleries/:galleryId/images')`, every handler `@Version('1')` (real path `/api/v1/galleries/:galleryId/images`), class-level `@Auth(VALID_ROLES.ADMIN)`. Params `galleryId` and `id` use `ParseUUIDPipe`. Endpoints: `POST /`, `GET /` (PaginationDto + galleryId), `GET /:id`, `PATCH /:id`, `DELETE /:id`. All operations resolve the parent gallery first (404 if missing), which satisfies the "image belongs to a single gallery" rule and keeps the unique `image_url` global. Alternative considered: a flat `/gallery-images` controller with `galleryId` in the body — rejected because the business models images as content *inside* a gallery and every read/activity is per gallery.

- **Service mirrors `galleries.service.ts`:** inject `Repository<GalleryImage>` + `Repository<Gallery>` + `CommonService`; `handleExceptions` for DB errors, `NotFoundException` for unknown gallery/image, `ConflictException` when `image_url` is duplicated. `create` forces `active: false` by default; activation/deactivation via `PATCH`. `findAll` filters by `galleryId`, orders `position ASC` then `createdAt ASC` (position-less items default to 0 and sort first), paginates with `PaginationDto`. `update` guards the unique `image_url`. `remove` deletes the record and returns only a confirmation message. `findById`, `create`, and `update` return the image **without the parent `gallery` relation** — a plain object stripping the `gallery` key — because TypeORM embeds the joined `Gallery` when the query filters by the relation (`where: { gallery: { id } }`). `galleries.service.remove` mirrors this: it returns only a confirmation message. Deleting a gallery continues to go through `galleries.service.remove`, and the DB `ON DELETE CASCADE` removes its images.

- **DTOs** use `class-validator` following `create-gallery.dto.ts`/`create-video.dto.ts`: `title` required (min 3), `imageUrl` required (`IsUrl`), `imagePublicId` required (`IsString`), `active` optional (`IsBoolean`), `position` optional (`IsNumber` + `IsPositive`, values ≥ 1; omitted values fall back to the DB default 0 and sort first). `UpdateGalleryImageDto` via `PartialType(CreateGalleryImageDto)`.

- **Migration:** generated via `bun run migration:generate --name=create_gallery_images_table` (timestamped, plural table name per convention), applied with `bun run migration:run`. Generated SQL creates `gallery_images` (FK `ON DELETE CASCADE`, unique `image_url`, `position int NOT NULL DEFAULT 0`). The applied file was regenerated by hand with the singular name `1788743764576-create_gallery_image_table` (table name remains `gallery_images`; this is a cosmetic deviation from the naming convention).

## Risks / Trade-offs

- Unique `image_url` collisions on create/update → reuse the existing conflict-check pattern (404 gallery + `ConflictException` on duplicate), same as galleries/videos.
- Deleting a gallery silently removes its images → intentional (confirmed with the product owner); the DB FK `ON DELETE CASCADE` guarantees consistency and avoids orphaned rows.
- Registering an image for a deleted/unknown gallery → resolved up front with a 404.
- TypeORM `@OneToMany` between modules requires importing the `GalleryImage` entity class from `gallery-images` into the `galleries` module for the type; keep it type-only (`import type`) to avoid a runtime coupling issue within the module graph.

## Migration Plan

1. `bun run migration:generate --name=create_gallery_images_table` → inspect the generated SQL (FK `ON DELETE CASCADE`, unique `image_url`) → `bun run migration:run`.
2. Rollback: `bun run migration:revert` drops `gallery_images`; the `galleries` table is untouched.

None. Delete-cascade and metadata-only scope were confirmed with the product owner; the field set was specified by the request.
